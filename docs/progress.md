### Phase 16 — Post-playtest overhaul: no noise, continuous campaign combat, prologue — DONE (2026-09-10)

Not on the original plan — direct user feedback after playing the Phase 13/14 build, given as 8 numbered items. All of this is scoped to **campaign only** — endless mode's wave rooms, travel corridor, gates, hazards, sleepers, noise/threat, and suppressor are all byte-for-byte unchanged; every new code path is gated on `runMode === "mission"`.

- [x] **Noise/suppressor removed (campaign only).** `addNoise()`/`wearSuppressor()` early-return for `runMode === "mission"` — `threat` simply never leaves 0, which for free disables every other threat-gated behavior (sleeper wake-on-noise, the Screamer's noise-triggered alert, the tier-2/3 crate lock, the gate quiet-bypass window) without touching those call sites individually, since campaign no longer has gates/sleepers to begin with (see below). `Hud.tsx`'s suppressor bar and noise meter both wrap in `{!hud.campaignMode && (...)}}`, matching the Phase 14 XP-bar precedent. Endless mode's noise/suppressor system is untouched.
- [x] **Campaign's exploration + Terminal Defense stages are now one continuous walk to a checkpoint, not wave rooms.** New `startCampaignTravel()`/`updateCampaignTravel()`/`reachCampaignCheckpoint()` replace `startTravel()`/`updateTravel()`/`reachSafeHouse()` for `runMode === "mission"` only (endless keeps calling the originals, unmodified). Zombies spawn continuously from both sides via a timer feeding the existing `spawnZombie()` (its bidirectional off-camera placement was already there, just reused instead of queue-driven), not from `buildWave()`'s discrete queue — `zombieWeights()` was extracted out of `buildWave()` so both paths share one weight table. A stage's `power` is set once for its whole walk (`difficultyFor` at the stage's mid-wave-equivalent) rather than escalating wave-by-wave, since there are no more waves. The Terminal Defense stage (`stageDef.fixedCamera`) starts the same way; reaching its checkpoint calls the **unmodified** `beginRest()`, which — because `fixedCamera` is true — drops straight into `"prep"` and the existing arena/boss/deployable/scrap loop exactly as it always worked. Every other stage's checkpoint calls the existing `completeStage()`/`missionComplete()`.
- [x] **Obstacles — jump over them, not shoot them.** First attempt made them destructible (hp, bullet collision, a hp-bar sprite) but that requires the auto-aim system to ever target something that isn't a zombie or the boss, which `acquireTarget()` flatly doesn't do — with no zombie in the lane, `onTarget` is false and auto-fire never fires, so a shootable obstacle with nothing nearby to shoot would soft-lock the player against it forever. Reworked to a much simpler mechanic that needed zero new targeting code: `Obstacle { x }` blocks ground movement only while `p.grounded`, and is skipped entirely while airborne — so it's cleared by timing the single jump (Phase 16 also restored earlier) over it, with a `[W] JUMP` prompt drawn above it once the player is close. Placed periodically along the walk in `startCampaignTravel()`.
- [x] **Zombie kills drop health/ammo pickups in campaign, not XP.** `gainXp()` was already a no-op there since Phase 14, so the old purple XP gem the user asked about was doing nothing when picked up in campaign — confirmed by reading `updateGems()`: `drawGem()` didn't even branch on `Gem.kind`, every gem (xp/scrap) rendered as the same purple diamond. Extended `Gem.kind` to `"health" | "ammo"`; `killZombie()` rolls a 28% chance for one of either (50/50) instead of xp gems when `runMode === "mission"`; pickup heals 20 hp (capped at `st.maxHp`) or calls the existing `awardSupply(0.25, 1)` (previously arena-only, now reused for a world pickup too). `drawGem()` gained a small kind→palette table (green for health, amber for ammo, unchanged violet/gray for xp/scrap) so the four kinds are now visually distinct, not just differently-colored pickup particles as before.
- [x] **Single jump.** `jump()`'s cap changed from `p.jumps >= 2` to `>= 1` — one line, no other double-jump state existed anywhere (checked: no upgrade grants extra jumps, no HUD jump-count indicator). Fixed the stale "DOUBLE JUMP" control hint on the Menu.
- [x] **Campaign's HP regen — already existing, no change.** Confirmed via the clarifying question: Phase 14 already added `CAMPAIGN_REGEN = 1.5`/`CAMPAIGN_MAX_HP = 160`; the user's ask was answered by that already being campaign-only, not extending it to endless.
- [x] **Hideout terminal opens from anywhere.** `updateHideout()`'s `terminalNear = Math.abs(p.x - terminalX) < 60` became an unconditional `terminalNear = true` — `App.tsx`'s `E`-opens-terminal handler already just checks `hud.terminalNear`, so no other change was needed there. The `[E] ACCESS TERMINAL` canvas prompt (drawn at the terminal's fixed position) is now always visible in the room rather than only up close, which is the correct look for "works from anywhere."

The arena's own wave/spawn balance has always assumed the defender starts at the fixed frame's *left* edge (`advanceStage()`'s old `worldW * 0.12` placement) with room to fall back as adds spawn from both screen edges; starting pinned at the right edge with zero retreat room caused a fast, repeated death loop in the very first arena wave.
